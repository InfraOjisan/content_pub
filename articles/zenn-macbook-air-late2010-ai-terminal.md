> この記事のMacBook Airは **11インチ・Late 2010** です。
> 
> 古いMacをモダンなGUIマシンとして延命する話ではない。AIエージェントに仕事を頼むための、軽くて静かな「端末」に戻した記録である。

## はじまりは、自宅から出てきた1台

自宅で15年もののMacBook Airを見つけた。

バッテリーは完全に死んでいた。ストレージも飛んでいた。それでもCPU、メモリ、液晶、キーボードは生きている。電源につなげば起動し、画面もちゃんと表示される。

「これはもう使えないPC」ではなく、「入出力装置としては、まだかなり良いPC」なのではないかと思った。

![MacBook Airの画像](https://storage.googleapis.com/zenn-user-upload/REPLACE_WITH_IMAGE_01.png)


目標は、現行OSのデスクトップを快適に動かすことではない。ネットワークの向こうにあるLLMを使い、ターミナルでAIコーディングをするための持ち運べる端末にすることだった。

## 最初にぶつかった壁は「軽量Linuxなら軽い」の嘘

この世代のMacBook Airは、OS XならLionまでが正規の守備範囲だ。現代的なLinuxを入れても、素直にはいかない。

いくつかの軽量ディストリビューションを試したが、グラフィックとWi-Fiがとにかく鬼門だった。起動はできても、ドライバがきれいに収まらない。軽量をうたうOSなのに、起動まで2〜3分かかることもあった。

唯一「比較的まともに動く」と感じたのはBodhi LinuxとChromeOS系だった。

- ChromeOS系(ChromeOS Flex)はライブ環境ではWi-Fiが見えても、内蔵ストレージへ入れると認識しなくなる。おそらく汎用ドライバは動作するがインストール時に親切に（おせっかいに）Broadcomのドライバを入れて失敗してるのだろう。ChromeOSはユーザーからここに関与するのは難しい。
- Bodhi Linuxは動作こそ軽いが、安定性とアプリ導入にかなり気を遣う。GUIがあまりにも特殊すぎる上に大半のアプリはソースからmakeする羽目になる。これあとで分かったのはBodhiの問題ではなくCPUアーキテクチャ（命令セット）の問題だったように思う。もちろん古いPCなのでコンパイルに異様に時間がかかる。

ここで発想を変えた。GUIを捨てればよい。

ブラウザ、IDE、ウィンドウマネージャをローカルで動かす必要がなければ、古いGPUやデスクトップ環境との相性に付き合う理由はほぼない。だって今自分の普段使いMacBookやWindowsマシンでのコーディングやライティングはターミナルベースなのだから。

## Ubuntu Server 24.04にしたら、急に快適になった

最終的に選んだのは **Ubuntu Server 24.04 LTS**。GUIなし、CUI専用である。

これが意外なほど快適だった。余計なものを描画しないので、古いCPUでも「入力して、通信して、結果を読む」作業に限れば遅さがあまり気にならない。まずSSHを有効にして、別のマシンから面倒を見られる状態を早めに作ったのも効いた。

とはいえ、日本語JISキーボードの設定は一筋縄ではいかなかった。

素のLinux TTYは日本語表示に向かず、日本語入力もそのままでは扱いにくい。Kana/EisuキーはXKB上では見えていても、ターミナル用IMEまで届かない。そこで最終的に次の構成に落ち着いた。

```text
Ubuntu Server 24.04 LTS
  └─ kmscon（日本語を表示できるローカルコンソール）
      └─ uim-fep + Mozc（日本語入力）
          └─ tmux（作業場）
```

IMEの切り替えはKana/Eisuキーではなく、`Ctrl+Space` にした。tmuxのプレフィックスは `Ctrl+q`。`Ctrl+q` が端末のフロー制御に奪われないよう、XON/XOFFも無効にしている。

ここまで来ると、ローカル画面でも日本語を読み書きでき、SSH経由でも保守できる。古いMacを「画面の付いたサーバー」として扱えるようになった。

![tmuxとAIコーディングCLIを表示するMacBook Air](https://storage.googleapis.com/zenn-user-upload/REPLACE_WITH_IMAGE_02.png)


## AIコーディングエージェントにも、古いCPUの地雷があった

OSが動いても、次はAIコーディングCLIでつまずいた。

この世代のCPUでは、現代のバイナリが期待する命令セットを満たせないことがある。Claude Code、OpenCode、omp、agyなど、試したツールの多くはこの壁で動かなかった。

またCodexは実行できるところまで行ったものの、ブラウザを使うOAuth認証が前提で、このCUI専用機では実用にしづらかった。これは性能不足というより、認証フローと端末の設計が噛み合わなかったという話だ。

最終的に使えたのは、次のCLIだった。

- **Qwen Code**
- **Crush**
- **pi**

実際にはNode.jsを入れ、Qwen CodeとCrushをグローバルに導入した。APIキーはプロジェクトごとに散らさず、ホームディレクトリ配下の権限を絞った設定ファイルから読むようにした。

「AIコーディング端末」と言っても、推論をこのMacBook Airでしているわけではない。端末はコードを読み、プロンプトを送り、返ってきた変更を確認する。重い計算はネットワークの向こう側にある。その分業なら、15年前のCPUでもまだ戦える。

## 最後に、バッテリーとSSDを交換した

ソフトウェアの道筋が見えたところで、死んでいたバッテリーとストレージを交換した。この時代のMacBook Airは11"と超コンパクトモデルでも簡単に分解メンテが可能なのだ。

![バッテリ交換中のMacBook Air](https://storage.googleapis.com/zenn-user-upload/REPLACE_WITH_IMAGE_03.png)


これでACアダプタに縛られず、持ち出して作業できる。薄い11インチの筐体、打ちやすいキーボード、十分な解像度の画面。ローカルで大型アプリケーションを何本も動かさないなら、いま見ても気持ちのよい道具だ。

![作業机で現役復帰したMacBook Air](https://storage.googleapis.com/zenn-user-upload/REPLACE_WITH_IMAGE_03.png)


## 15年後に戻ってきた「ダム端末」

昔は、PCがすべてを抱え込んでいた。CPUが速く、GPUが強く、ローカルのGUIアプリが充実していることが正義だった。

いまは少し違う。AIエージェントとクラウド側の計算資源を使うなら、手元に必要なのは必ずしも最強のマシンではない。

- ちゃんと打てるキーボード
- 読める画面
- 安定したネットワーク
- 長時間使えるバッテリー
- そして、ターミナル

時代が2周くらいして、CPUもGPUもGUIも最小限でよい「ダム端末」の時代に戻ってきたように思う。

もちろん、巨大なリポジトリのローカル解析、Dockerの多重起動、ブラウザを何十タブも開く仕事には向かない。それでも、AIと対話しながらコードを書くという用途に絞れば、このLate 2010のMacBook Airは驚くほど現役だ。なんといっても軽量でコンパクトで頑丈で入力が快適だ。おそらく最新のiPadよりも。
でも他の方におすすめするならMid2011以降が良いと思う。中古の価格は大差ない上にキーボードバックライトがあるからだ。加えて4GBモデルの個体が多い（Mid2011からIntel統合グラフィックになってメインメモリを少し余分に使うからかも）。
Late2010とMid2011はバッテリーに互換性がないので要注意。コネクタ形状は同じなのにボード上のコネクタ位置が変わって差さらない。バッテリーを購入するときは型番まで確認して商品写真をよく確認して、万一の時に返品可能なストアを選ぼう。

古いPCを蘇らせるとき、最新のデスクトップ環境を無理に載せる必要はない。役割を変えればいい。これは15年前のMacBook Airを、2026年のポータブルAIコーディング端末に仕立て直した記録である。

## 構成メモ

再構築時の構成は以下。

```text
MacBook Air 11-inch Late 2010
Ubuntu Server 24.04 LTS (amd64)
kmscon + Noto Sans Mono CJK JP
uim-fep + Mozc（Ctrl+Spaceで切り替え）
tmux（Ctrl+qをプレフィックスに設定）
SSH / Tailscale
Qwen Code / Crush / pi
```

同じ世代のMacで再現する場合は、まず有線EthernetかスマートフォンのUSBテザリングでネットワークを確保し、OpenSSHを有効にするのは必須だ。画面が不調になっても、別マシンから復旧できる。そもそも設定のコピペが段違いに楽なのだ。
